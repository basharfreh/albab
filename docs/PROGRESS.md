**Decisions / deviations** (none of these are spelled out precisely in the brief; each is a judgment call made to fill a real gap)
- **"Active listing" for quota purposes** = status in `{pending, published, paused}`. Excludes `draft`/`rejected` (not yet consuming a slot) and `sold`/`rented` (the transaction is done; the slot should free up). This isn't stated in brief §7's one-line quota rule, but the alternative (sold/rented listings permanently consuming quota forever) seemed clearly wrong for a marketplace.
- **`GET /listings/map/` response shape**: brief §7 says the endpoint "returns `{"truncated": true}` when the bbox holds more [than 500]," which read literally would mean the response is *only* `{"truncated": true}` with no markers at all in that case. Implemented instead as an always-consistent `{"results": [...], "truncated": bool}` — markers are always present (capped at 500), `truncated` is always a boolean. A map that returns zero pins whenever there's "too many" would be a worse app, not a safer one.
- **Owner block's `created_at`**: brief §7 lists `ListingDetailSerializer` as adding "...owner block with name/avatar/phone/whatsapp_phone, created_at" — read `created_at` as belonging to the owner block (supports the "member since" UI text P8's mobile phase explicitly describes for this same owner block), not as a separate top-level field on the listing itself (the listing already has its own `created_at` via `TimeStampedModel`, so a second identically-named field would be ambiguous).
- **PATCH edit-ability**: brief §7 states plainly "PATCH edits while `draft|rejected|published`" — implemented as a hard 400 outside those three statuses (i.e. `pending`/`sold`/`rented`/`paused` are not owner-editable via PATCH). This is unambiguous from the brief text itself, just noting it since it's enforced in `perform_update`, not by DRF defaults.
- **No Django admin registration for `catalog` models** — P1's brief explicitly listed "Django admin registration" as a P1 task for `accounts`; P2's task list has no equivalent line item, so it was left out to stay in scope. (`manage.py shell` is sufficient for debugging until/unless a later phase asks for it.)
- Setting an existing (already-uploaded) image as cover after the fact has **no endpoint** — the fixed endpoint surface (brief §7) only has `POST images/`, `DELETE images/{id}/`, `POST images/reorder/`, and cover selection is only exposed as an optional `is_cover` flag at upload time. P9 (mobile wizard, "تعيين كصورة رئيسية") will need this; flagging it now rather than inventing an endpoint outside the brief's fixed surface.

## 2026-09-08 — Backend fix — the two P5-flagged auth bugs (apps/accounts)

**A real bug found only through live testing, fixed**

## 2026-09-12 — P12 — Flutter hardening: offline/failure behaviour (item 5)

Same multi-session day, continuing per the user's "كمل حسب الخطة" ("continue per the plan") after the accessibility-pass entry above. Picked up P12 item 5: "cached last map results, a connectivity banner, retry on every failed request, no infinite spinners."

**A real "infinite spinner" bug found in both paginated lists, fixed — plus a data-loss bug found while fixing it**
- `MapHomeScreen`'s `_ListingsListView` and `MyListingsScreen`'s `_MyListingsTab` both hard-coded their "load more" footer as an unconditional `CircularProgressIndicator` with no error branch. Once a `_loadMore()` request actually failed, `hasMore` stayed `true`, `loading` went back to `false`, and that spinner just sat there forever — exactly the "infinite spinner" brief P12 item 5 calls out, real and reachable (any transient network blip while scrolling a long list), just never visibly exercised before since nothing in either screen's own tests drove a failure that far.
- Fixing this exposed a second, worse bug underneath: both screens' `_loadMore()` incremented `_page` *before* the request (`_page += 1; await _load(reset:false)`), so a failed page's number was already consumed — a retry would have silently skipped straight to the *next* page, never re-fetching the one that actually failed. Restructured both to advance `_page` only on success (`_load` now takes an explicit `requestedPage`, defaulting to `_page + 1`, and only commits it to `_page` once the request resolves) — a retry now always re-asks for the exact page that failed.
- New shared `PaginationFooter` widget (`packages/albab_core/lib/src/widgets/pagination_footer.dart`): spinner while `hasError` is false, a tappable "تعذر تحميل المزيد، إعادة المحاولة" row wired to `onRetry` when it's true. Both screens now use it instead of their own inline `CircularProgressIndicator`. **Gave both states the same fixed height (56px)** — discovered empirically while writing the test below that letting the footer's height change between states shifts `maxScrollExtent` while the list sits at the bottom, which matters for *test* determinism (see below); kept the fix anyway since a jumping scroll position on a real device would be a small but real polish regression too.

**"Cached last map results" — the map already did this, silently; now it says so**
- `MapHomeScreen._fetchMarkers()`'s catch block already left `_markers` untouched on a failed refetch (only the success path overwrites it) — a pan or filter-change refetch failing while markers are already on screen was *already* falling back to the last good data, not going blank. The bug was that this was completely silent: nothing told the user they were looking at stale results. Added a `SnackBar` (`l10n.mapMarkersRefreshFailed`, "تعذر تحديث النتائج — يتم عرض آخر نتائج محفوظة") with a retry action, shown only when `_markers != null` (a first-load failure with nothing cached yet still gets the existing full-screen `ErrorState`, unchanged).

**Connectivity banner — genuinely new, nothing like it existed**
- Added `connectivity_plus` to `packages/albab_core`'s dependencies (also picked up transitively by `apps/dashboard`'s pubspec.lock, though this slice only wires it into `apps/mobile` — see Decisions). `connectivityProvider` (`StreamProvider<bool>`) wraps `Connectivity().checkConnectivity()` + `onConnectivityChanged`. `ConnectivityBanner` widget renders nothing while online (or while the state is still unknown — no flash on cold start) and a slim red bar with a wifi-off icon + "لا يوجد اتصال بالإنترنت" while offline. Wired once into `apps/mobile/lib/app.dart`'s `MaterialApp.router(builder: ...)`, so every route gets it for free rather than each screen wiring its own.
- Building for Linux desktop (needed for the still-open integration-test blocker from two entries ago) already required `libsecret-1-dev`; `connectivity_plus`'s own Linux implementation additionally pulled in `dbus`/`nm` packages via pub, no new system packages needed.

**A real, non-obvious test-infrastructure finding: `ScrollPosition.jumpTo` fires its listener twice**
- Writing a deterministic test for the pagination-retry fix (`map_home_screen_test.dart`'s new "a failed load more..." test) needed a way to reach the bottom of a list without a real drag/fling (whose deceleration fires the scroll listener an unpredictable number of times as it settles — no test should have to model that). Using the list's own `ScrollController.jumpTo(maxScrollExtent)` directly is deterministic, but *itself* still fires the attached listener (and so `_loadMore()`) **twice**, not once — confirmed by direct instrumentation, reproducible identically across three consecutive runs. This is a `ScrollPosition` framework behavior, unrelated to anything in this codebase; the test now asserts the real `[1, 2, 2]` sequence (and `[1, 2, 2, 2]` after a manual retry) rather than fighting it down to a wrong assumption of exactly one call. **Worth flagging for any future test that scrolls a list this way**: don't assume one `jumpTo` means one scroll-triggered side effect.
- Also needed a longer real-time pump (500ms, not the file's usual 50ms) after the jump — two chained failed attempts, each with its own microtask-deferred `await`, needed more than 50ms of simulated time to both fully resolve before the widget tree reflected the final error state. A `pumpAndSettle()` was deliberately avoided here: `CircularProgressIndicator`'s indeterminate spin animation schedules frames forever while it's on screen, so if this test ever regressed to a truly-stuck spinner, `pumpAndSettle` would hang instead of failing cleanly — a fixed real-time pump fails loud and fast instead.

## 2026-09-12 — P12 — Analytics review (item 6): a real cross-consistency bug found and fixed

Same day, continuing per "كمل حسب الخطة" after the offline/failure-UI entry above. Picked up P12 item 6: "confirm owner stats and admin KPIs agree on the same numbers." Backend-only this slice — nothing in either Flutter app changed, since both already just display whatever the API returns.

**Traced every place a "views"/"contacts" number actually comes from**, to find what could make two of them disagree:
- `Listing.views_count`/`contacts_count` — denormalised per-listing lifetime counters. Read by the admin's "أكثر العقارات مشاهدة" table (`AdminListingQueueView.ordering_fields`, sorts by `views_count`) and by the mobile "عقاراتي" row's views count.
- `ListingDailyStat.views`/`contacts` — per-listing-per-day rows. Summed by `owner_listing_stats` (P10's mobile stats screen) *and* `admin_visits_series` (P11's dashboard chart) — the same table, two different aggregations.
- All three only ever get written from one place: `apps/analytics/services/events.py`'s `record_event`.

**The bug**: `record_event` made three separate writes — `ListingEvent.objects.create(...)`, `ListingDailyStat.objects.get_or_create(...)` + an `.update()`, and a `Listing.objects.filter(...).update(...)` — with no transaction around any of them. `grep`ping the whole backend for `transaction.atomic` found zero existing usages anywhere in this project, so this was never a deliberate omission, just never noticed: a dropped connection or a deadlock between any two of those three writes would leave `Listing.views_count` permanently disagreeing with what `ListingDailyStat` (and so both the owner stats screen and the admin visits chart) says — the exact failure mode this brief item exists to catch. **Fixed** by wrapping all three writes in one `transaction.atomic()` block (`apps/analytics/services/events.py`) — they now either all land together or none do.
- Did not touch the *separate*, pre-existing "two concurrent requests could both pass the throttle check before either commits" race in the same function (a real but different issue — a narrow double-count window, not a cross-table consistency one). Left alone deliberately, matching this project's own precedent for an analogous race in P5's phone-registration flow (see that entry above: "out of scope... the unique constraint is the last line of defense... concurrency control [wasn't] the fix requested").

**Two new backend tests** (`apps/analytics/tests/test_events.py`) prove the fix rather than just asserting it compiles:
- `test_denormalized_counters_stay_in_sync_with_the_daily_rollup` — posts a mix of view/call/whatsapp events (two views from different IPs, so neither gets throttled) and asserts `Listing.views_count`/`contacts_count` exactly equal `Sum(ListingDailyStat.views/contacts)` for that listing.
- `test_owner_totals_and_the_admin_visits_series_agree_on_the_same_numbers` — goes through the *real* `/me/listings/stats/` and `/admin/analytics/visits/` endpoints (not just the model layer) for one owner's one listing and asserts both sides' 7-day totals match exactly — the actual brief wording, checked end to end.
